# House of Cards — working rules for Claude Code sessions

Read this fully before doing anything. Sessions in this repo do not share memory with the design conversations that produced these rules, so this file is the handoff.

## What the game is
- Alternate 1867 Canadian Confederation. Fictional noble houses hold peerages over real federal ridings (343 ridings, 2023 Representation Order).
- The game director issues one-line directives. Claude writes narrative and executes the mechanics.
- At migration baseline: 33 active houses, 2 historically removed houses, roughly 145 ridings claimed. Societal climate most recently at −1 Significant Conservative (following the Regulation 17 / Ontario Bilingual Schools Crisis event). Narrative era roughly 1867–1918 on house personal clocks.

## Source of truth
- The original workbook no longer exists. See `scenarios/legacy/RECONSTRUCTION.md`.
- `hoc.db` is canonical (Phase 3 complete). Everything in `outputs/` is regenerated from it.
- `hoc.db` is a derived artefact: `python scripts/rebuild.py` reconstructs it from scratch out of the active scenario's `seed/*.csv` plus `data/reference/*.csv` and then replays that scenario's record (`turns/` for the reconstructed game, `seasons/` for an engine-played one). The seed CSVs and the turn/season files are the reproducible record; the database is what they produce. The seed CSVs remain the audited input and the record of provenance — do not edit their values; add reconstructed data only in the manner described in scenarios/legacy/RECONSTRUCTION.md, then rebuild.
- Which game the database holds is `scenarios/current.txt`; switch with `python -m hoc scenario use <name>`, then rebuild. Which game may still be *written to* is a different question, answered by manifests (see Scenarios below). Two games are frozen: `legacy` is the reconstructed playthrough, `new` is **The First Dominion**, the engine-played game (seed 1867, seasons 1–150). **`dominion` — The Dominion — is live**: an engine-played game on the `meridian-v1.0.3` world under rules 0.9, seed 1867, its first house seated by the engine's own draw. Everything below about turns applies to the legacy scenario.
- Game state produced by turns lives in the turn files and, once applied, in `hoc.db` (events, turns, narrative). The seed is never regenerated from the database.

## Hard rules (these have all been broken before and corrected by hand)
1. Never fabricate. No house attributes, riding names, relationships, dates or colours that are not in the data. If something is missing, record it as missing (e.g. TBD) and flag it in your final status.
2. Riding names must match the 2023 Representation Order exactly. Names change over time (e.g. West Nova no longer exists; the current riding is Acadie—Annapolis). Validate against the `ridings` table once it exists; before that, flag anything you cannot verify.
3. Expansions require land adjacency to an existing holding. Water-only adjacency is a fallback that must be flagged, never silently accepted. Non-adjacent proposals are rejected before any narrative is written.
4. Primary colour of a house is the colour of its principal seat, which is the first of its ridings in canonical row order. Do not use count-based or rarity rules; they break on ties.
5. No universal calendar. Each house has its own personal clock starting at 1867. Clocks sync only on direct shared events between named houses. Global events never sync clocks. On succession the new holder's clock resets to personal 1867; biological ages are not reset.
   This rule does not apply to a game played with rules 1.0's `world_calendar`, where one turn is one year for every house (see Rules 1.0 (draft) below).
6. Founding grants must be evaluated for cohort fit against the current climate state before execution. This is mandatory, not advisory.
7. Rank ladder and remaining mechanics are defined in Mechanics Sections 1–3 of the baseline workbook. Extract them in Phase 1; do not guess them.
8. The game runs more than one era-cohort of Section 10 events in parallel (see scenarios/legacy/RECONSTRUCTION.md). Never collapse the climate ledgers into one number; always state which era-cohort a climate value belongs to.
9. A turn narrative may use house detail only if it is in hoc.db (house_blocks, holders, holdings, relations, events). Detail supplied in a directive that is not yet in the database must be added to scenarios/legacy/seed/house_blocks.csv in a reconstruction commit in the same PR before the turn is applied.

## Scenarios, live and frozen

- A scenario is a directory `scenarios/<name>/` with a manifest `scenario.json` read by `hoc/scenario.py`. Its fields: `name`, `title`, `status`, `reference_data`, `seed`, `started_season`, `kind` (`director` or `autoplay`), and whatever a scenario adds to say how it began (`rules_version`, `restarted`, `note`). Keep every existing field when extending one.
- **`status` is `"live"` or `"frozen"`; a missing status reads as frozen.** At most one scenario is live (`scenario.live_name()` is `None` when none is, and raises when two are). **Only a live scenario is ever written to** — seasons played, interventions applied, turns applied, a save from the browser — and `scenario.require_live()` is the one refusal, raising `FrozenScenarioError`. `hoc.db` must also hold the live scenario for a writer to play on it; `current.txt` and `status` are separate facts.
- `reference_data` names the reference-table set the scenario's seed was built against: `ne-2026` (`data/reference/`) or `meridian-v1.0.3` (`data/reference/meridian/v1.0.3/`). `scenario.reference_dir()` resolves it and every loader reads through it — see World data below.
- **No code names a scenario.** The engine workflow, the console, the play page, the referee and the exporters take the live scenario from the manifests (`scenario.live_name()`), and the archive takes every frozen one (`scenario.frozen_names()`). `tests/test_frozen.py` greps for `scenarios/new` and friends in `hoc/`, `web/`, `scripts/` and `.github/`; do not add one. Tools that need an empty world and no particular game use `scenario.blank_seed_dir()`.
- **Freezing a game** is: set its manifest's `status` to `"frozen"` (and give it a `title`), nothing else. Do not rename its directory, touch its season or intervention files, or edit any rules version it was played under — the referee must still replay it byte for byte (`python scripts/referee.py --all --scenario <name>` proves it, changing nothing).
- **Beginning a game** is: create `scenarios/<name>/` with a manifest (`status: "live"`, `kind: "autoplay"`) and header-only `seed/*.csv`, `python -m hoc scenario use <name>`, `python -m hoc sim new --seed N`. Only then do play.html and console.html become playable again.
- With **no live scenario**, `play.html` and `console.html` are plain notices saying so (and linking the Archive); no engine, rules, reference map or world snapshot is shipped, and a previous export's are swept. The engine workflow, `hoc sim run/new`, `hoc apply`, the browser's Save and the console's dispatch all refuse a frozen game, with a message on the page where there is one. The referee refuses a push that writes a frozen scenario's record (`scripts/referee.py --refuse-frozen`).
- **Frozen games are archived, not deleted.** `outputs/site/archive/index.html` lists them and `outputs/site/archive/<name>/` is each one's whole site — map, houses, ridings, chronicle (narratives included), climate — rebuilt from its own record on every export by `scripts/build_archive.py`, which sends the replayed season logs to a scratch directory and never over the committed record. A live scenario is never archived. Narrating a frozen game (`python -m hoc narrate A B --scenario <name>`) is allowed: it writes `narratives/`, not game state.

## World data

- **The ground a game is played on is a reference-data version**, named by the scenario manifest's `reference_data` and registered in `hoc/scenario.py`'s `REFERENCE_SETS`. A manifest without the key reads as `ne-2026`. Every reader goes through it: `scripts/load_seed.py` loads the set's ridings and adjacency and records the set in `hoc.db`'s one-row `reference_data` table; `sim.World` reads its designation tables from the set its database recorded (`places.reference_dir_for(conn)`), never from `current.txt`; the site map, the play page's shipped tables (`hoc/export/play.py`'s `reference_files`) and the world snapshot (`reference_data`) follow the same row. The browser always reads the live game's set at `data/reference/`.
- **`ne-2026`** is `data/reference/`: the 2023 Representation Order from Elections Canada's boundary file, clipped to Natural Earth's coastline (`raw/SOURCE.md`). Both frozen games were played on it and must keep it.
- **`meridian-v1.0.3`** is `data/reference/meridian/v1.0.3/`, built from Meridian's riding unit table (github.com/mdiamond95/meridian, tag `v1.0.3`; its `docs/interop.md`, "Unit tables", is the contract). `scripts/fetch_meridian.py` downloads the table and its riding layer into `raw/`, refuses any other SHA-256 and any table whose format, version or unit is not `meridian.unitTable` / 1 / `fed_2023`, and records the tag, URLs and hashes in `raw/SOURCE.md`. The files are committed: nothing is fetched at play time, in a CI replay or in the browser. `scripts/build_world_meridian.py` builds the tables beside them: `ridings.csv` and `adjacency.csv` byte-identical to `ne-2026`'s, `places_by_riding.csv` with census places and a `spans_ridings` column, `riding_tokens.csv`, and two new tables — `riding_stats.csv` (integers only) and `riding_jurisdictions.csv` (one row per span, in whole years). Both engines load the two new tables. From rules 0.9 the season loop reads `riding_stats.csv`'s `opens_year` and `wealth_tier` (see Jurisdiction and endowments below); `riding_jurisdictions.csv` is read for display only, and `resource_tier` by nothing in the game yet.
- **No float from Meridian reaches an engine.** Every number is parsed as a `Decimal` and turned into an integer once, at build time, by the rule in `docs/DETERMINISM.md` ("Reference data from Meridian"). Never round or rank Meridian values anywhere else.
- **Meridian's GDP figures are an allocation, not a measurement**: provincial GDP by industry shared over ridings by census labour force (`allocation_v1`). The game carries GDP only as `wealth_tier`, a quintile; anything that shows it must say so, with the table's `gdpCaveat`. There is no `cohesion` in a unit table and none is invented. `areaKm2` is land area (`land_area_km2`). A place whose population exceeds its riding's (Halifax under Central Nova) is marked `spans_ridings = 1`; a place whose name is census bookkeeping rather than a place ("Division No.  1, Subd. U", "Yarmouth 33", "Cariboo I") fails the text rule in `docs/DETERMINISM.md`. Either way its `designation_ok` is 0, and both engines offer only `designation_ok = 1` places as designations, in the seat's tier and the neighbours'. A failing name is never rewritten to pass (hard rule 1).
- **Drawing files are not game data.** A set's tables that an engine reads (`ridings.csv`, `adjacency.csv`, `places_by_riding.csv`, `riding_tokens.csv`, `riding_stats.csv`, `riding_jurisdictions.csv`) are closed once a scenario on them has a season. Its drawing files (`geometry_simplified`, `borders_shared`, `geometry_site`, `borders_site`, all `.geojson`) are read by the map exporters and by nothing else — neither engine imports or reads a `.geojson` file (`tests/test_meridian.py` checks) — so they may be corrected. `meridian-v1.0.3` carries none of its own: Meridian's layer is the unclipped Elections Canada file and fills Hudson Bay, so `hoc/export/map.py` (`_drawing_path`) draws every set without its own drawing files from the coast-clipped ones in `data/reference/`, the same 343 ridings. `scripts/build_world_meridian.py` writes no geometry.
- **The `meridian-v1.0.3` tables are closed for good.** The Dominion played its first season on them, so `scripts/build_world_meridian.py` may no longer rebuild that directory: any change — a column, a rule, a row — is a new reference-data version.
- **`meridian-hex-v1.0.5` is the hex board** (`data/reference/meridian/hex-v1.0.5/`, docs/hex-trial/v2/README.md), which the director chose over ridings. It is built by `scripts/build_world_hexboard.py` from the five files `scripts/fetch_meridian.py --board` pins:
  - Meridian v1.0.5's regenerated resolution-4 hexagons (`hexes.r4.v1.2`: large lakes and straits as water, settlement dates);
  - the city hexes (`hexes.r5.v1`);
  - their two layers;
  - the mesh (`mesh.v1.json.gz`, each cell's census subdivision).

  What it holds:
  - **Units.** 494: the 423 hexagons of 5,000 people or more under 500,000, and of the 16 at 500,000 or more, the city hexes of 25,000 or more and each parent's most populous cell, its core. Ids are nine digits (docs/DETERMINISM.md, "The hex board on v1.0.5").
  - **Names.** A city or core hex is named for its own mesh municipality, never a neighbouring one, and never with a riding token. Where several share one, the holder of its place keeps the plain name and the others add the compass word of their bearing from it: "Ottawa", "Ottawa West"; "Gatineau" across the river. On a shared bearing the farther is "Outer", then a numeral.
  - **Opening years.** `opens_year` is the latest of the atlas, `settledYear` (a city hex's is its municipality's; only for land under Canada after 1867, and only to 1930), and, for every hex of a city's municipality but its plain-named one, the city year. The director's twelve overrides beat every part.
  - **Water.** `adjacency.csv` keeps a water row only for a water link of 3 hexagons or fewer, plus the director's ferry (Cape Breton–Stephenville, for Channel-Port aux Basques); every water link is in `links.csv`. Every island group but Iqaluit reaches the mainland through the rows.
  - **Resolution.** `riding_stats.csv` carries each unit's `resolution` (4, or 5 for a city hex), which `block_grants` reads.
  - **Drawing files.** In the six table shapes, plus `units.csv`, `links.csv`, `hexes.geojson`, `routes.geojson`, `jurisdictions.geojson` (the first-order borders and names for each span of years the atlas holds still) and `set.json`, read by the exporters only.
  - **Where it plays.** No scenario is played on it. The hex preview (`outputs/site/preview-hex/`, built beside the riding preview by `scripts/build_preview.py`) and `scripts/story_trial.py --reference meridian-hex-v1.0.5` play scratch worlds.
  - **What reads it.** Its `set.json` names the unit ("holding"); the story layer reads it through the beat index (`unit_word`, `web/story/words.js`), and a set without one says "riding". The founding roll's denominator is the map's unit count in both engines (`World.total_units`, `map.ridings.length`), 343 on the riding sets. `tests/test_hexboard.py` holds the set.
- **`meridian-hex-v1.0.4`, the first hex trial's set, was removed** on 10 October 2026, when the preview moved to v1.0.5. Its record is docs/hex-trial/README.md, with the trial table as measured.
- **Moving the pin to a newer Meridian tag is a new reference-data version, never an edit to an old one.** Copy the two scripts' pin (tag, hashes) forward, fetch into `data/reference/meridian/<new tag>/raw/`, build that directory, register `meridian-<new tag>` in `REFERENCE_SETS`, and point a *new* scenario at it. Never re-fetch into, rebuild or hand-edit a version a game has been played on: the referee replays a game against the tables it was played on, and a changed table is a different game. `tests/test_meridian.py` rebuilds the committed tables and fails on any byte that differs.

## Autoplay

The engine plays the **live** scenario (see above); at the time of writing that is `dominion`, The Dominion, and `python -m hoc scenario list` says which, if any, is live.

- **Only the engine workflow, the referee workflow or a Code session may commit game state.** `rules/` and `outputs/` change through `.github/workflows/engine.yml` (dispatched from the site's console, or by hand) or through a session working to these rules. **`hoc.db` and `outputs/` are written only by those two workflows or by a session** — never from a browser. The play page may commit the *record* (`scenarios/<live>/seasons/` and `scenarios/<live>/interventions/`) and nothing else; `.github/workflows/referee.yml` then replays it with the Python engine and publishes it only if every season matches byte for byte. A browser can propose a game; it cannot publish one.
- The workflow takes four commands: `run` (play seasons, halting on any armed stop condition), `intervene` (apply a director's turn file between seasons), `rules` (patch numeric fields, bump the version, append a CHANGELOG entry) and `rebuild` (replay the record and verify it reproduces `hoc.db`). It runs the suite with `-m "not smoke"` and exports before it commits, so a failing run commits nothing. The 300-season smoke run stays here, in Code sessions.
- No model is called by any workflow. The console's Narrate control produces a block of instructions for a person to paste into a Claude Code session; that is the whole of Claude's part in the running game. A narrative written that way lands in `narratives/NNNN-NNNN.md` and may use house detail only from `hoc.db` (hard rule 9).
- A director's intervention into an engine-played game is recorded at `scenarios/<live>/interventions/NNNN.json`, named for the season it follows, whichever engine played the game — the console writes there and so does the browser. `scripts/rebuild.py`'s `record_interventions` is the single definition of what the record contains, and `scripts/referee.py` reads it rather than looking for the files itself.
- Seasons are run only through `python -m hoc sim run N`. Never advance the game by editing the database, and never hand-write a season file — `scenarios/<live>/seasons/NNNN.json` is written by the engine as its audit trail, and `scripts/rebuild.py` replays the game from the world seed to check it.
- `python -m hoc sim status` says where the game stands. `python -m hoc sim run N --stop-on removal,challenge,major,marquis` stops early on anything worth the director's attention.
- Hand-written turn files remain available for director interventions — a grant, a correction, a scripted event. Apply one **between** seasons with `python -m hoc apply <turnfile>`, never in the middle of a run, and commit it with the database as any turn is. An intervention on the live game is named `NNNN_sSSSS-<slug>.json`, where SSSS is the season it follows: `scripts/rebuild.py` reads that to replay it back into the right place between two seasons.
- The intervention operations are `set_objective`, `veto_objective`, `force_action`, `adjust_stat` (which will not apply without a reason), `grant_house`, `set_clock` and `relation`. Expansion, succession, elevation and the climate ledger are the engine's own business — a director who wants those runs seasons.
- **Rules are versioned, and a season is always replayed under the rules it was played with.** `rules/current.txt` names the version new seasons use; `rules/versions/<v>/` holds that version's tables; every season file records its `rules_version`, and every replay path loads that version. Tuning the game means **copying the current version directory to the next one**, changing the copy, pointing `current.txt` at it, and recording it in `rules/CHANGELOG.md` with the metric that motivated it. **Never edit a published version's tables** — that rewrites history, and the referee will refuse seasons that were correct when they were played. `scripts/apply_rules_patch.py` (the console's Rules control) does the fork for you. It never means editing `hoc/sim.py`.
- A change in *algorithm* rather than in a number goes behind a named boolean in that version's `features.json`, false in every earlier version, with the old code path left reachable in **both** engines. `hoc/rules_data.py`'s `FEATURE_DEFAULTS` and `web/engine/rules.js`'s must agree, and every default is false. See `rules/README.md`.
- Never edit `hoc.db` by hand. It is derived: the seed CSVs plus the season logs (and any turn files) are the record, and the database is what they produce.
- The reconstructed 2026 playthrough is frozen in the **legacy** scenario and published at `outputs/site/archive/legacy/`, beside The First Dominion at `outputs/site/archive/new/`, rebuilt on every export. `python -m hoc scenario use legacy` switches `hoc.db` back to it for reading; the turn procedure below is about that game, and `hoc apply` will not write to it while it is frozen.

## Jurisdiction and endowments (rules 0.9)

Two flags in `rules/versions/0.9/features.json`, false in 0.7 and 0.8, with the old path reachable in both engines. Both read the reference set's `riding_stats.csv`; on a set without it (`ne-2026`) every riding opens at 1867 and every `wealth_tier` reads 3, so they change nothing there. `docs/ENGINE_DESIGN.md` §18 is the full account; `rules/CHANGELOG.md` 0.9 holds the trial that motivated them.

- **`atlas_jurisdiction`: a house reads the map at its own personal year.** A riding is *closed* to a house while the house's personal year is before the riding's `opens_year` (1867 for 269 ridings, 1870 for 74).
  - A Crown founding (season 1, the founding roll, `grant_house`) seats a house only where `opens_year` is 1867 — a new house's clock reads 1867. In `p_found` and the region weights, "unclaimed" means unclaimed and foundable; the formula still divides by 343, and reaches zero when the foundable map is full.
  - Expand never offers a closed riding: it is filtered out before any draw (`World.open_expansion_targets`), and Expand is legal only when an open target exists. Enclosure (§7b) is unchanged — closed neighbours still count as unclaimed land.
  - Cadet foundings by partition, transfers, absorption, compacts, disputes and every other shared event are not gated. A clock reset never takes away, penalises or disables anything a house holds.
  - `grant_house` on a closed riding, and a forced Expand when every unclaimed neighbour is closed at the year the house will act in (next season's personal year), are refused with a message naming the riding, the personal year and the `opens_year`.
  - Display only: season records (an Expand outcome's and a founding event's `jurisdiction`, the `founding.jurisdiction` log entry), house pages, the map and the Narrate block name a riding by the jurisdiction in `riding_jurisdictions.csv` at the relevant house's personal year; a chronicle line adds it in brackets only when it differs from today's ("takes Avalon (Newfoundland)"). The engine keys on `ridings.csv`'s province code, never on a jurisdiction name.
- **`riding_endowments`.** Founding capital is `30 + 5*rank_index + d20 + 2*(wealth_tier − 3)` of the seat; a successful Expand costs `15 + (wealth_tier − 3)` of the target. The failure cost and the capital ≥ 40 precondition are unchanged. `resource_tier` is exported (`outputs/dump/state.json`'s `ridings`) and shown on the ridings page, and read by nothing else. `wealth_tier` is shown nowhere, being Meridian's GDP allocation rather than a measurement.
- The slow West is intended: with no Crown grant beyond 1867 ground, the Prairies are opened by expansion from Ontario, Quebec and British Columbia over a century of seasons. Do not add a "frontier grant" without the director asking for one.
- `tests/test_atlas.py` holds a test for each of the above.

## Rules 1.0 (draft)

- `rules/versions/1.0/` is a **draft** (docs/STORY_DESIGN.md §4, Phase C1): `upkeep_phase`, `holder_traits`, `marriage_pairing`, `prestige`, `founding_curve` and `succession_watch`, each false in `FEATURE_DEFAULTS` and in 0.7–0.9, in both engines. `rules/current.txt` stays at 0.9 and no committed game plays a season under 1.0, so its tables may still be tuned; it is frozen like any version the moment one does. At most one draft version exists (`tests/test_rules_versions.py`).
- Phase C2 added `schemes`, `contested_claims`, `prestige_politics` and `cohesion_strain`; Phase D1 adds `distinct_surnames`, `world_calendar` and `crises` (docs/STORY_DESIGN.md §4.10, §5, §5.1), on the same terms.
  - **`world_calendar`**: one turn is one year from `game.json` (1867, 100 turns, five chapters, which are the era bands). Events fire by world year for every house; an event with a `through_year` repeats its direct effect each year. One climate ledger (`world`). The atlas is read at the world year from `riding_jurisdictions.csv`, which is not changed: a riding is in play while its sovereign is Canada, and the Crown founds only in a province. After turn 100 the engine writes the reckoning, and `hoc sim run` refuses turn 101. Personal clocks remain, as reign years, and nothing reads them.
  - **`crises`**: a Major event is a crisis every house takes a side in; the camp with more influence carries it. It reads the world year, so it does nothing without `world_calendar`.
  - Phase D1's follow-up tuned the draft's tables only: a crisis side reads `game.json` `crises.response` (symmetric Lead/Resist thresholds), and `schemes.json` `elevation` lets a petition reach Duke on holdings that rise with rank. Both engines read them with the old terms as the default.
  - The cross-check plays 1.0 for its 100 turns (`tests/test_crosscheck.py`, `.github/workflows/ci.yml`).
  - The story layer reads the calendar from the beat index (`calendar`, `reckoning`): headings by year, a chapter interstitial at each chapter's end, and the reckoning after the last turn (`web/story/reckoning.js`).
  - The preview (`scripts/build_preview.py`) is the draft's whole game, 1867–1966, with its Reckoning page.
- **`dated_openings`** (the hex board, on the same terms):
  - Under `world_calendar`, a unit takes no grant, expansion or claim before its opening year. That year is the later of `opens_year` and its first year under Canada, and the unit is open for good from it: the Ontario–Manitoba disputed area stays open through 1881–1889. A Crown founding still needs a province.
  - A unit opening after it came under Canada opens as a quiet world event (`world: "opening"`, the story layer's `opening` beat).
  - On the riding sets it repeats the atlas, except for a riding the atlas takes out of Canada and back (Nunavut 1876–1879, Labrador 1927–1948). `tests/test_dated_openings.py` holds it.
- **`water_crossings`** and **`block_grants`** (the hex board, step 3, on the same terms; their numbers in the draft's `board.json`):
  - `water_crossings`: a water row of `adjacency.csv` joins two units for expansion targets, claim targets and neighbouring houses, and an Expand across water costs `expand_cost` more. Enclosure, cohesion and contiguity stay land only.
  - `block_grants`: a Crown founding on a resolution-4 hexagon also grants up to `extra_hexes` open, unclaimed resolution-4 neighbours, the most populous first. A city hex is granted alone.
  - Both change nothing on the riding sets, which have no water rows and no `resolution` column. `tests/test_board_flags.py` holds them.
- Phase V2 adds `round_record` on the same terms: every engine event's delta carries `part` (`"world"`, the house whose turn it is, or `"close"`) and every season record carries `order`. It records and decides nothing (`tests/test_round_record.py`; docs/DETERMINISM.md, "The round record"). The cross-check compares every engine event as well as every season file.
- The Dominion stays live on 0.9. Beginning a game under 1.0 means pointing `current.txt` at it in the same change that begins that game.
- `tests/test_rules10.py` holds each flag; the cross-check runs under 1.0 as well as 0.9 (`tests/test_crosscheck.py`, `.github/workflows/ci.yml`).
- `python scripts/story_trial.py --matrix` plays ten seeds of 100 turns on scratch Meridian worlds and prints the trial table recorded in `rules/CHANGELOG.md` under 1.0 (draft). It writes nothing to any scenario. `--c2` and `--d1` print the Phase C2 and D1 comparisons; `--prepend` adds a column measured on other code. `--c2` prints Phase C2's before/after table.
- **Phase C2** adds four flags, false in 0.7–0.9 and on in the draft (STORY_DESIGN §4.2, §4.4, §4.5, §4.9):
  - `schemes`: a house holds at most one public multi-turn scheme from `schemes.csv`, chosen by an integer utility (`schemes.json`), in place of the weighted action draw.
  - `contested_claims`: a claim resolves as a contest; a seat can be taken, and a house with none falls.
  - `prestige_politics`: houses read prestige.
  - `cohesion_strain`: cohesion falls with holdings beyond a rank's reach.
- The action handlers stay the schemes' resolution primitives. A scheme's events carry `{"scheme": {...}}` in their delta, and each season record carries `plans`. The world snapshot (`hoc/export/world.py`) carries the schemes table.
- The story layer types scheme, ally, contest and fall beats (`hoc/export/beats.py` and `web/story/beats.js`, which must agree), and shows **Plans afoot** for a record with schemes.
- **The draft-rules preview.** On every export, `scripts/build_preview.py` plays 100 seasons of the draft (seed 1867) on a scratch Meridian world and publishes them at `outputs/site/preview/` (Replay and Storylines), linked as "Preview (draft rules)".
  - It is not a scenario: it writes no season file, nothing under `scenarios/` and nothing in `hoc.db`, and every page says it is not a game of record.
  - It disappears when no draft version exists.

## Playing (Phase 10-2)

- **`outputs/site/play.html` is the primary way to play.** It runs `web/engine/` in the browser against `outputs/site/data/world.json`, computes every season on the device, and is regenerated by `python -m hoc export` like every other page.
- Play in the page stays in that browser until the director saves it. **Save** commits the season files and any intervention files, as one unforced fast-forward of `main` through the Git Data API, and nothing else; the referee workflow verifies them against the Python engine before `hoc.db`, `outputs/` and the site move. A save refuses rather than merging when `main` has moved past the base the browser played from, and Undo refuses to rewind past a saved season — rewriting saved history would need a force-push, which this repository does not do.
- `web/engine/record.js` is the single definition of what a save writes, of what the autosave keeps, and of how a game is replayed forward from the committed base. Change it and `web/engine/savecheck.js` and `web/engine/restorecheck.js` check it headlessly with the network mocked; the play page must not build those paths, bounds or replays itself.
- A season record that has been through storage has lost the `FloatValue` boxes round §10's two genuine floats, because IndexedDB stores a structured clone and JSON stores text. Revive it (`reviveRecords`) before serialising, or `canonicalJson` refuses it.
- The play page never disables Save and never returns from it silently: every refusal writes to `#save-status`, and a permanent line under the button says where the token, the browser and the repository stand.
- **The page and the console write only to the live scenario.** `web/engine/record.js` derives the record's paths (`scenarios/<name>/seasons`, `scenarios/<name>/interventions`) from the scenario it is handed and throws `FrozenScenarioError` from both `recordFiles` and `commitRecord` unless that scenario's `status` is `"live"`; the exporter hands the page its scenario as `{name, title, status}`. `web/engine/savecheck.js` proves the refusal against every non-live manifest in the repository, and the page says so in `#save-status`.
- **The console's GitHub-Actions path stays.** It is the reproducible one — every season it plays is committed, tested and replayable from the record — and it is what a device without the JavaScript performance for a 300-season run can use. Neither path replaces the other.
- `hoc/export/world.py` decides what the browser is given. It carries what the engine reads and nothing else; if a season ever reads something new, add it there and `tests/test_world_snapshot.py` will tell you whether you were right.
- The play page's assets are copied into the site on export (`hoc/export/play.py`). The browser cannot reach `web/`, `rules/` or `data/reference/`, so a module, a rules table or a reference table added to the engine has to be added to that list too. Every rules version is exported, under `data/rules/versions/<v>/`.

## Two engines (Phase 10)

There are two implementations of the engine and they must play the same game.

- **Any change to `hoc/sim.py` must be mirrored in `web/engine/sim.js` in the same PR, and the cross-check must pass.** The same goes for `hoc/prng.py`, `hoc/palette.py`, `hoc/names.py` and `hoc/rules_data.py` against their `web/engine/` counterparts.
- `python scripts/crosscheck.py --seed 1867 --seasons 120` runs both engines and diffs their season files byte for byte. `tests/test_crosscheck.py` runs it for three seeds; `tests/test_js_engine_parity.py` checks the primitives underneath at a much finer grain — when both fail, fix the parity test first, because it names the primitive rather than the season.
- **Never fix a divergence by loosening the comparison.** The cross-check ignores exactly one field (`engine.impl`), and a test asserts that the ignore list has not grown. If the two engines disagree, one of them disagrees with `docs/DETERMINISM.md`; fix that one.
- Nothing in either engine may use a float, a language's sort order, a hash table's iteration order, or a locale. `docs/DETERMINISM.md` is the contract; read it before changing anything that draws.
- `web/engine/` is plain ES modules with no build step and no dependencies. An import of anything but a relative path or a `node:` builtin breaks the browser, and a test guards it.

## Story layer

- `docs/STORY_DESIGN.md` is the design for the story game (rules 1.0). Phase A — beats, story weight, the dispatch, standings, following, the archive's Replay pages — is built, and is presentation only.
- **Architecture rule (§3): the story layer is one implementation, in JavaScript, at `web/story/`.** It is a pure function of the game's record, runs in the browser and under node for tests, and never feeds back into either engine, so it is outside the two-engine parity contract. Anything a house's decisions depend on is engine state and belongs in both engines (§4). `web/story/` imports nothing from `web/engine/`, and neither engine imports it (`tests/test_story.py`).
- Beats are typed from the structured record (event kind, `event_houses`, `mechanical_delta`, the holdings an event moved, the acting house's action), never from chronicle prose: by `hoc/export/beats.py` for exported and archived games and by `web/story/beats.js` for the play page. Change one, change both; `tests/test_story.py` requires them to agree.
- **Phase V: the Replay is a map** (docs/STORY_DESIGN.md §3.6). `replay.html` is the map view: the map fills the screen, `web/story/marks.js` turns a dispatch into marks (pure, tested under node), and `web/story/camera.js` holds the follow/free camera, the framing, card placement and gestures. The text Replay is `replay-text.html`. The exporter ships each house's seat history and a calendar game's jurisdictions in `data/beats/atlas.json`, and the fuller geometry in `data/map-detail.json`. `tests/js/mapview.e2e.mjs` (run by `tests/test_mapview.py` where Playwright is installed) is the browser check.
- **Phase V2: the year as a round** (docs/STORY_DESIGN.md §3.6). For a record with `round_record`, the Replay tells each year as it is played — the world's turn, each house's turn in `order`, the close — with a turn-order strip, a house sheet and the paces (`web/story/round.js`). The database keeps `part` but not `order`, so whoever exports such a game hands `write_beats` the season records' orders (`scripts/build_preview.py`, `scripts/build_archive.py`). Any other game is told a year at a time.
- **Phase V3: pace and wording of the round** (docs/STORY_DESIGN.md §3.6). A house's turn has one of four paces — quiet, routine, notable, pause — by what happened in it, not by the headline weights alone; which beat kinds belong to which, and how long Auto holds and the camera flies for each, are in `web/story/weights.json` (`pace`), never in code. The year's event is a tag on a card, a card's sentences start at the verb (`text.js` `verbFirst`; the text Replay, drawer and year in brief keep full sentences), and the close carries a count line (`round.js` `yearCounts`). A house's response beat carries the event's name as `world.event` (`beats.py` and `beats.js` agree).
- `web/story/weights.json` is the story's own tuning, read by no engine. Hard rule 5 stands for every game but one played with `world_calendar` (§5), which the next scenario will be (Phase D2).

## Conventions
- Canadian English spelling throughout (colour, honour, centre, defence).
- Narrative for a turn is about 500 words, rich prose, not bullet lists; the runner warns above 550 words and refuses above 600.
- Mechanics Section 5 house-block updates are short-form appends: Holdings always; Economic when operation type changes; Political when named political figures attend or relational events occur; Cultural only for genuinely new nodes. Transaction log entries stay detailed.
- Section 13 watch items: zero or one per turn, only for genuinely unresolved structural questions.

## openpyxl pitfalls (relevant to extract.py and the workbook exporter)
- `insert_rows()` does not update merged cell ranges. Unmerge every range at script start, re-merge at the end.
- After any row insert, previously cached row numbers are invalid; re-find rows by content search.
- Section header searches must confirm the character after the section-number prefix is uppercase, to avoid matching list items.
- Section 5 house blocks are 9 rows (house name row plus 8 labelled rows), starting around row 36; match on the surname before the " — " delimiter in column A. Some column B cells are intentionally None; guard with `current or ""`.
- The house matrix (Section 9) data rows are tightly bounded to actual house rows; do not let loops capture annotation text beneath the matrix.
- The adjacency register (Section 10) is single-column, label-only.

## Working pattern
- One build step or one game turn per session. Work on a branch, commit with a clear message, push, open a PR.
- Make one commit per logical change; keep the diff reviewable on a phone.
- Never modify values in `scenarios/legacy/seed/` except through a reconstruction commit as defined in scenarios/legacy/RECONSTRUCTION.md.

## Turn procedure
This is the legacy scenario's procedure (historical: that game is frozen, and `hoc apply` refuses a frozen scenario), and the procedure for a director intervention in whichever game is live. Run a game turn in exactly these steps. The format of a turn file is in docs/TURN_FILE.md.

1. **Read the state first.** Run `python -m hoc status`, then read `outputs/dump/state.json` for the houses the directive touches — holder, generation, clock, holdings, colours. Write nothing until you have.
2. **Check any expansion before writing it.** Run `python -m hoc check <house> <riding>`. If it fails, pick another riding that the data supports, or stop and report the problem to the director. Never write narrative for a move that has not passed the check. Water-only adjacency passes with a warning — surface that warning in your status block, never bury it.
3. **Write `scenarios/legacy/turns/NNNN_<slug>.json`.** Operations first, then the narrative. The narrative is Canadian spelling, about 500 words, rich prose rather than bullet lists, anchored only in what the data records — no invented settlers, dates, relations or colours. Dates are personal years on the house's own clock; there is no universal calendar, so never write a shared year for houses that did not meet.
4. **Apply it.** `python -m hoc apply scenarios/legacy/turns/NNNN_<slug>.json`. This validates, applies and re-exports in one transaction. If it fails, fix the turn file and run it again. Never edit `hoc.db` by hand, and never hand-edit anything in `outputs/`.
5. **Commit `hoc.db`, the turn file and `outputs/` together**, so the database and its generated views never disagree. Push, open a PR.
6. **Give the director the narrative in full in the message, then close with the STATUS block.** The narrative goes in the body so it can be read in chat without opening the repo; the STATUS block stays last, as the section below requires.
